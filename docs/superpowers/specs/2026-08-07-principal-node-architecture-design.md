# RDMA-P2P: Principal/Node Architecture with P2P Bitswap

**Date:** 2026-08-07
**Status:** Draft
**Branch:** fm/rdma-p2p-interface-e-openai

## Overview

Transform the current peer-to-peer architecture (where every node is autonomous and self-assigns layers) into a **Principal/Node** model with:

1. **Startup flow** — role selection via minimal web UI, persistent JSON config, no auto-loading
2. **Connection authentication** — shared connection key, principal validates node handshakes
3. **API key system** — separate keys for OpenAI-compatible requests, with tracking foundation
4. **P2P bitswap transfer** — torrent-like chunked file transfer for model shards over libp2p
5. **Node management** — principal can block/unblock, verify shard integrity, track disk space
6. **Improved web UI** — role-aware dashboard, node management tab, notifications, transfer progress

## Design Decisions

- **Approach:** Pragmatic Hybrid — keep existing UDP + libp2p + HTTP transport stack, add auth/config/bitswap modules on top
- **Config format:** JSON (`rdma-p2p.json` in working directory or `$RDMA_P2P_CONFIG`)
- **Chunk size for bitswap:** 4 MB per chunk, SHA256 hash per chunk, MD5 hash for full file
- **Connection key:** Persisted, regenerable by principal, SHA256-derived from Ed25519 + nonce
- **API keys:** Single active per node (generating new deactivates old), stored with tracking metadata

### Mode: Setup (no config file exists)

1. Binary starts, reads `rdma-p2p.json` — not found.
2. Starts a **minimal HTTP server** on `--gateway-port` (default 8080).
3. Serves a single setup page (`web/setup.html`, embedded via `include_str!`) with two options:

   **"Principal":**
   - Generates connection key: `SHA256(Ed25519::signing_key.to_bytes() || random_nonce)` → 64 hex chars
   - Gathers local IPv4 and IPv6 addresses
   - Displays: key, IPv4, IPv6 on the page
   - User clicks "Iniciar" → writes `rdma-p2p.json`, restarts process in full mode

   **"Node":**
   - Shows form: principal address input + connection key input
   - On submit: `POST /handshake` to principal with `{ node_id, pubkey, connection_key }`
   - If approved (200): writes `rdma-p2p.json`, restarts in full mode
   - If rejected (403): shows error on screen (invalid key, blocked)

### Mode: Full (config file exists)

Skips setup HTML, starts full stack.

**Principal flow:**
1. Load config → generate/load Ed25519 identity → bind UDP + libp2p → start gateway with all routes
2. Expose admin routes, node management
3. Generate first API key if none exist
4. Listen for node handshakes (periodic, every 30s)

**Node flow:**
1. Load config → generate/load Ed25519 identity → connect to bootstrap nodes
2. Send handshake with connection key
3. If rejected (key changed or blocked): show reconnection/blocked screen
4. If approved: enter normal mode (announce, wait for layer assignment, etc.)

## Section 2: Connection Lifecycle & Auth

### Connection Key

- Generated by principal via `SHA256(signing_key_bytes + random_nonce)`
- Stored in `rdma-p2p.json`
- **Regenerable**: `POST /admin/regenerate-key` → invalidates all active sessions
- Nodes must re-handshake on failure

### Handshake Protocol

```
POST /handshake
Body: { node_id, pubkey, connection_key }

Response:
  200 { approved: true, peer_id }
  403 { reason: "invalid_key" | "blocked" }
```

**Principal side** (`src/session.rs`):
- Validates `connection_key` against config
- Checks `node_id` not in `blocked_nodes` list
- If OK: registers node as verified, stores pubkey

**Node side:**
- Sends handshake on connect and every 30s
- On 403 `"invalid_key"`: show reconfiguration screen (key was regenerated)
- On 403 `"blocked"`: show blocked screen, stop trying

### Auth Middleware (`src/auth.rs`)

Two-tier:

| Tier | Scope | Header | Validates Against |
|------|-------|--------|-------------------|
| Connection (internal) | `/admin/*`, `/api/ui/apply`, `/api/ui/launch`, `/api/ui/plan` | `Authorization: Bearer <connection_key>` | Config connection_key |
| API (external) | `/v1/chat/completions`, `/v1/completions`, `/v1/models` | `Authorization: Bearer <api_key>` | Active API keys |

### API Keys

- Structure: `{ key: "sk-...", label: string, node_id: string, active: bool, created_at: ISO8601 }`
- **Single active at a time**: generating a new key deactivates the previous (`active: false`)
- Inactive keys kept for historical tracking (future: token consumption analytics)
- Generated by both principal and nodes
- Nodes announce their API keys to principal via gossip for centralized validation

Routes:
```
# Principal
GET    /admin/api-keys          → list all keys (all nodes)
POST   /admin/api-keys          → generate new { label } → { key }
DELETE /admin/api-keys/:key     → revoke

# Any node
GET    /api-keys                → list own keys
POST   /api-keys                → generate new { label } → { key }
```

## Section 3: P2P Bitswap Transfer

### Protocol Design

**Chunking:**
- File divided into 4 MB chunks
- Each chunk identified by `SHA256(data)`
- Manifest sent before transfer: `{ file_name, total_size, chunk_size, num_chunks, chunks: [{ index, offset, size, sha256 }], md5_full }`
- MD5 of complete file for final integrity check

### Flow: Push (Principal → Node)

```
Principal                                  Node
  |                                         |
  |-- POST /admin/transfer-offer -------->|
  |   { shard_name, start_layer,          |
  |     end_layer, total_size_mb,         |
  |     num_chunks, manifesto_sha256 }    |
  |                                         |
  |   Node checks disk space               |
  |   Shows notification in UI:            |
  |   "Principal wants to send             |
  |    qwen_0_15.gguf (2.3 GB).            |
  |    Free space: 45 GB."                 |
  |                                         |
  |<-- 200 { accepted: true }   OR  ------|
  |    409 { error: "disk_full",          |
  |          available_mb, required_mb }   |
  |                                         |
  |   If accepted:                          |
  |-- libp2p bitswap parallel send ----->|
  |   up to 8 concurrent chunks            |
  |                                         |
  |<-- ACK/NACK per chunk ---------------|
  |   (retry on checksum failure)          |
  |                                         |
  |-- (complete) final manifest -------->|
  |<-- 200 { verified: true,             |
  |     md5_match: true }                 |
```

### Flow: Pull (Node → Principal)

```
Node                                        Principal
  |                                           |
  |-- GET /catalog/shards/:model ---------->|
  |<-- [{ name, range, size, chunks }] -----|
  |                                           |
  |   Node picks shard in UI                 |
  |                                           |
  |-- POST /transfer-request -------------->|
  |   { shard_name, node_id }               |
  |                                           |
  |<-- 200 { manifesto, chunks[] } ---------|
  |                                           |
  |-- libp2p bitswap download (parallel) -->|
  |   (no approval needed — node initiated)  |
  |                                           |
  |   Verify MD5 locally after completion    |
```

### Implementation (`src/bitswap.rs`)

New libp2p behaviour registered in the swarm:

```rust
struct BitswapBehaviour {
    want_list: HashMap<PeerId, HashSet<ChunkId>>,
    blocks: HashMap<ChunkId, Vec<u8>>,
    pending_requests: HashMap<RequestId, oneshot::Sender<Result<Vec<u8>>>>,
    served_blocks: HashMap<PeerId, u64>,  // for fairness/throttling
}
```

**Protocol messages** (bincode-encoded):
```rust
enum BitswapMessage {
    WantList { chunks: Vec<ChunkId> },
    Block { chunk_id: ChunkId, data: Vec<u8> },
    Have { chunks: Vec<ChunkId> },
    Cancel { chunks: Vec<ChunkId> },
}
```

**Transfer events** emitted to gateway:
```rust
enum TransferEvent {
    ChunkReceived { chunk_id: ChunkId, from: PeerId },
    ChunkFailed { chunk_id: ChunkId, reason: String },
    TransferComplete { manifest_sha256: String, md5_verified: bool },
    Progress { pct: f32, bytes_received: u64, bytes_per_sec: f64 },
}
```

**Config:**
- Max concurrent chunks per peer: 8
- Chunk size: 4 MB (4 * 1024 * 1024)
- Request timeout: 30s per chunk
- Max retries per chunk: 3 before trying another peer

## Section 4: Node Management & Machine State

### Extended Machine State (`sysmon.rs`)

```rust
struct DiskInfo {
    total_mb: u64,
    free_mb: u64,
    mount_point: String,
}
```

### Extended PeerInfo

```rust
struct PeerInfo {
    // Existing fields ...
    node_id, pubkey, addr, model,
    start_layer, end_layer, total_layers,
    memory_mb, ollama_port, inference_port, gateway_port,
    last_seen,
    
    // New fields
    role: Role,                    // Principal | Node
    hostname: String,
    connection_verified: bool,
    disk_total_mb: u64,
    disk_free_mb: u64,
    api_keys_active: u16,
}
```

### Block/Unblock Nodes (Principal)

```
GET    /admin/nodes                  → list all (verified, blocked, pending)
POST   /admin/nodes/:id/block        → block (rejects future handshakes)
POST   /admin/nodes/:id/unblock      → unblock
DELETE /admin/nodes/:id              → remove permanently
```

Blocked node behavior:
- Current connection continues until next periodic handshake
- Next handshake returns `403 { reason: "blocked" }`
- Node UI shows blocked screen

### Shard Integrity Verification

```
GET /admin/verify-shards
```

For each node and each shard:
1. Request MD5 of local file from node
2. Compare MD5 across all nodes with same shard
3. Compare layer ranges (start/end)
4. Return report with consistency status

Response:
```json
{
  "model": "qwen35",
  "total_layers": 32,
  "consistent": true,
  "shards": [
    { "range": [0, 15], "md5": "abc123", "peers": ["node_a", "node_b"], "match": true },
    { "range": [16, 31], "md5": "def456", "peers": ["node_c"], "match": true }
  ],
  "warnings": []
}
```

If inconsistent → UI shows alert, inference launch is blocked.

### Slice-and-Distribute Workflow (Principal)

1. Principal selects model from catalog
2. Defines shard count based on connected nodes
3. `plan.rs` computes asymmetric division
4. `split_model.py` extracts each shard **locally on principal**
5. For each shard: `POST /admin/transfer-offer` to target node
6. Node UI shows notification → accepts → bitswap transfer starts
7. After all transfers: global MD5 verification
8. Only then: "Launch" button enabled for inference
